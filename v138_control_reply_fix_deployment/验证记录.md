## 1.0.2 再次检查结论

1.0.1 已处理现场日志中动作 `rejected` 经本机 TTS 播报的问题，以及接受控制后使用模型否定回复、SDK 完成异常追加错误的路径。但再次审查发现，仍有以下边界缺陷，需要使用 1.0.2 替代旧增量包。

| 新发现 | 旧包复现结果 | 本次修复 |
| --- | --- | --- |
| 迟到的重复控制回调 | 短去重窗口过期后再次唤醒讲解并请求模型；可能误暂停任务，模型异常还会追加服务不可用语音 | 同一事件和文本在 60 秒内已被控制链路接管时，在唤醒讲解/模型/任务匹配前结束；模型返回或失败后再次检查并发接管 |
| 导航启动回执丢失 | 接口已收到 POST，Java 将 HTTP 异常当作可重试，第二次可能返回 busy 并播报 | 网络/解析异常不重发；仅明确布尔 `accepted=false` 的暂态拒绝有限重试 |
| 空或损坏控制回执 | JSON 异常、空对象或 null 可能造成 5001，或回落到模型的“做不到” | 校验各控制接口布尔字段；未知结果只记诊断、不发失败、不称成功 |
| 否定/转述讲解指令 | “不要开始讲解”“他说开始讲解”会因子串规则启动任务 | 本地匹配与执行前共同保护，模型误判也不能触发；保留礼貌请求和明确停止 |
| 错误备份回滚 | 其他 release 的备份可能先停止服务再拒绝 | 停止前核对备份归属 |
| 修补文件与运行代码不一致 | 原检查能证明 current JAR 已替换，但不能排除 systemd 覆盖仍使用旧 JAR | 安装前检查生效的 ExecStart；安装后检查实际进程 classpath 和主类，未知覆盖拒装，不自动删除 |

故障测试直接加载已交付 1.0.1 归档中的 JAR，使用真实 AgentSDK 1.4.0 回调和序列化，连接本机模拟 HTTP 服务。相同的 524 条断言中，旧包 248 条未通过，新包全部通过。这些断言覆盖不同回调、语音通路与故障组合，不是 248 个独立缺陷。旧包复现输出保留在构建工作目录 `work/previous-audit.log`。

## 1.0.1 代码检查结论（历史记录）

导航和讲解被本地控制器接受后，旧逻辑仍允许使用意图模型生成的回复，并且没有像动作请求一样保留“本地已接受”标志。结果可能出现否定确认语，或在后续 SDK 完成回调异常时发送 5001 错误。

旧版原生动作中断只覆盖明确的预设动作词及标准讲解词，没有覆盖导航、自定义讲解匹配和模型识别的灵活动作。控制请求的去重也没有统一覆盖这些类型。重复回调的完成事件发送失败还会进入错误处理。

结合用户提供的 `lingxi-log-20261018-1015-1027.zip` 进一步确认：
两次“比个心”的底层拒绝文本由 `/motion/play` 结果直接流入 `/tts/speak`。
1.0.0 仍会把这类回执翻译成“暂未被接受”，因此不能覆盖用户要求的
底层兜底播报静默。1.0.1 补充静默策略，并将“已接受”和
“该回执已经处理，不应再发 SDK 错误”分别记录，拒绝状态不被伪装成成功。

现场还出现 10 次模型 HTTP 超时。基线已有故障处理，本次保留并用真实
15 秒 HTTP 超时验证精确点位处理及问答服务不可用提示。
日志中的 Python 文件为空，且 Java 文件混合多个时间片段和活动地图，
不能证明物理动作回执异常的底层原因或所有原生播报来源。
详细证据见同目录 `日志核验说明.md`。
