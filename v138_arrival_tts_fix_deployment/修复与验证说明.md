# 1.0.7 修复与验证说明

## 对应现场证据

依据 2026 年 10 月 19 日 15:05:07 导出的日志：

- 15:02:56，取号点距离约 0.359 米，等到 120 秒超时。
- 15:04:56，门口距离约 0.424 米，等到 120 秒超时。
- HTTP 先返回 `accepted=true,status=submitted`，随后 PlayTts 回调显示 `priority_rejected`。
- 15:00:27 的启动讲解请求实际被已有导航拒绝；15:00:56 是另一次请求启动的任务，不能把二者视为同一次成功请求。
- 15:01:19 已有讲解任务，以及 15:01:40 讲解保护拒绝新导航，属于正常保护，本次保留。

日志所用 JAR 是累计 1.0.5；本包同时补入累计 1.0.6 的导航地点、讲解启动意图修复。

## 到达判定

保持严格半径和原有严格进圈后的迟滞逻辑。在没有进入严格圈、机器人已停在 0.45 米以内的情况下，新增受约束的 5 秒稳定收尾。不会把“到达失败”一律改成“到达成功”。

收尾要求有效姿态、有效朝向、有限数值、新鲜且推进的 ROS 时间戳、连续采样、低线速度、低转速和受限的位置漂移。采样断流、重复/过期/倒退时间戳、运动、转向、漂移或超出距离都会重置证据。复用现有 STOP 和停稳等待，只触发一次完成事件；取消、超时或 PNC 失败已经终结的会话不会被迟到定位改为成功。

## 语音确认

- `accepted=true` 只在 PlayTts 返回真正的布尔成功时给出。
- 明确拒绝会保留原因；确认缺失、格式异常或确认超时不伪装为成功。
- 只有 HTTP 工作线程等待确认，ROS 回调继续异步执行，避免等待自己的 executor。
- 明确的优先级拒绝最多重试两次，优先级保持 L7，不提高到最高优先级；任务切换或请求过期时停止重试。
- 不确定的提交不会由 Java 重发，也不会重新开启 SDK 文本播报，避免迟到回执造成双重播放。
- 讲解中的回复若确认丢失，仍保留有上限的播放等待，再计算完整的静默时间，避免直接恢复讲解压住可能正在播放的回答。
- 控制执行结果与语音接收结果继续分开，语音拒绝不被转换为“导航/动作/任务执行失败”。

本包不把 PlayTts 接收确认等同于播放完成，也不宣称已证实并拦截来源不明的系统原生道歉。

不覆盖网页、地图、任务数据、知识库和配置；不是从其他 V1.3.9 逻辑直接移植。

## 验证

构建执行完整 Python 回归和全部 16 个 Java 回归套件。最终归档再次验证内部 SHA256、LF 换行、脚本和说明命令语法、Java 17 字节码、交付源码重新编译一致性，并在 Linux 临时根目录验证多文件事务安装、服务状态保持、真实用户读取权限、未知文件拒绝、备份损坏拒绝及失败回滚。

详细数量和最终归档 SHA256 以 `交付验证结果.json` 为准。机器人实机验证未在本次执行，未远程安装或重启现场服务。
