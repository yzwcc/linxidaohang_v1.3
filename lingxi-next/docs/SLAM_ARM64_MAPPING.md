# ARM64 真机全局点云地图保存与重载

日期：2026-10-28。结论：**机器人本机四轮真实记录的 GLIM CPU 全局点云地图
保存，以及机器人新进程中的完整地图重新加载均通过文件往返检查。**
相比 `SLAM_ARM64_RECORDED.md` 的纯里程计回放，本轮确实执行了子图构建、
全局 pose graph 保存与 CPU 加载，而不是以非空位姿或文件创建代替地图成功。
仍未通过标定、地图几何、回环、重定位、实时建图或自主导航验收。
0.1.18/0.1.19 产品后端、安装包和 APK 保持不变。

## 来源与运行边界

沿用同一批已经核对的静止/行走 bag、固定上游源码及 ARM64 CPU 核心。
`glim-mapping/mapping.cpp` 和 CMake 与此前电脑端持久化验证的源码完全相同，
只改变编译目标，不重写厂商或上游算法、不按本轮结果调参。
复用已验证的 ARM64 里程计 C ABI；配置、实际外参和诊断摘要
必须与此前真实记录回放包一致，两种扫描时间假设仍明确未批准。

新增建图适配库为 ELF64/AArch64，SHA-256：
`5eea694f5145e657d18848bf2d20eb94c81dd0867585e936d27e68e70a0acb84`。
目标普通用户进程实际执行，Python 3.10.12、NumPy 1.26.1。
库和实际配置只放在新的
`~/lingxi-next-validation-arm64-mapping-20261028-a/`，
目录 700、文件 600。既有核心目录和历史试验不改写。

使用 Humble bag 文件读取和消息反序列化，没有 ROS 初始化、节点、
实时传感器订阅、TF 发布或运动接口。不安装包、不使用 sudo，
不改 AIMDK、步态、安全链路、模式、输入源、服务、既有地图或点位。
用户无需再次行走。连接保留严格 SSH 主机身份验证和内存交互密码。
每轮沿用 nice 10、OpenMP/OpenBLAS 各 2 线程环境和 480 秒外层上限；
独立重载子进程另有 180 秒上限。不是系统级线程/CPU 硬配额。
四轮和所有重载子进程正常退出 0，SSH 协调器已关闭，没有新增常驻节点。

四轮录制/处理/跳过/初始化/有效位姿的完整计数与纯里程计阶段一致。
每个初始化成功帧只由官方 marginalized 回调送入一次；
EOF 原生关闭会发出余帧回调，不再次提交其返回列表。
本轮核对 `finalizedFramesFedOnce = savedFrames = 有效位姿数`，
保存的四份轨迹均完整、有限且严格按时间排序。

使用官方 `SubMappingPassthrough` 和 `GlobalMappingPoseGraph` 保存，
保存前对照点取自真实子图及保存位姿，不调用该 pose-graph 模块的空导出实现。
释放回调并退出上游线程后，机器人另起 Python 进程，以官方
`GlobalMapping::load/export_points` 在 CPU 上重载 pose-only 图。
核对两个进程 PID 不同、架构均为 AArch64、子图/因子/节点数量一致，
并逐点按完整点序比较全部点，不使用最近邻重配对或有利样本筛选。

序列化容差继续固定为 1e-4 原始坐标单位，不是按结果放宽的阈值，
也不是定位精度承诺。重载前后全部地图文件名称、大小和内容摘要一致；
原生及重载日志无错误、图自动恢复或损坏提示，上游默认参数警告保留。

## 尚未证明的事项

两种时间假设的子图数和点数明显不同，时间语义仍是未解决条件。
目标“扫描终点”行走结果为 10 个子图，而此前电脑结果为 9 个；
差异原因未判定，不将其自动归因为浮点计算，也不宣称跨平台地图几何一致。
目标地图的墙面重影、尺度、方向及轨迹需要独立参照验证。

保留默认 50 原始单位的最小回环候选行程；
两轮行走的子图中心累计行程仅约 2.6472 / 4.4109。
本试验不触发该阈值，不能证明回环有效；
源码会在超过短序列边界时报错，不把它当作通用长序列建图器。
文件成功往返也不证明启动后地图重定位或失定位恢复。

下一阶段仍需驱动扫描基准/单位/同步与外参核实、共同有效时段及几何对照、
Humble 实时封装、重定位、语音并发和长期负载测试。
导航另须受控验证控制权、失效停车、避障和硬件急停，
不能由本轮结果推导出可以接通速度接口。
任何后续移动、模式或输入源切换仍先取得现场确认。
