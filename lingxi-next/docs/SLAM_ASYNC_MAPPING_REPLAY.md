# 有界后台建图与修正点云回放

日期：2026-10-31。此轮在电脑的隔离 Linux x86_64 环境使用既有录制，
没有连接机器人、启动实时传感器、部署服务或发送运动指令。
完整产品、ARM64 接入和用户可见实时建图尚未验收。

## 实现

`tools/glim-async-mapping/` 复用上一轮源文件固定的完整 CPU `SubMapping`
与 `GlobalMapping`，保留相同末帧补丁、IMU、局部和全局优化配置。
不复制旧版产品业务代码，也不重写里程计、配准、优化或导航算法。

核对固定 GLIM 源码的 `AsyncSubMapping` 和 `AsyncGlobalMapping` 后，保留
后台执行思路，但不直接使用其无界输入容器。上游线程中的异常缺少本层
需要的传回路径，析构硬停止也不能替代显式的完整停止排空。
本轮让一个 FIFO 工作线程串行拥有两级映射，避免两个映射线程之间再加入
无界转发队列；后续只能基于测量决定是否进一步拆分，不靠并行数量作保证。
官方算法仍是固定 GLIM 实现，不改变其配准与优化参数以追求外观。

- 雷达里程计回调只克隆完成帧的元数据并入队，点数据按上游不可变共享所有权
  保留；重计算不在此回调执行。IMU 向量入队前复制，避免依赖调用方缓冲区。
- 容量为 128 个完成帧和 8,192 条 IMU，包含正在执行的任务；批量完成帧按
  实际数量计费，不以一个队列节点代替整批成本。
- 不等待优化来腾空入队空间。容量不足时锁存故障、拒绝继续采集，不静默丢帧、
  降低计数、扩大容量或把缺数据的结果保存成成功地图。
- 后台异常传回调用方。输入、快照查询、停止均检查锁存故障；失败停止不执行
  成功保存的终结步骤。队列保留接受、完成、拒绝与丢弃计数及最大等待时间。
- 停止顺序为：先停止 LIO 并接收全部剩余完成帧，再关闭队列入口、排空已接受
  输入，在同一工作线程结束子图、优化、保存。线程退出后才移除非线程安全的
  上游回调和释放映射对象。一个进程只允许一个会话、一次保存。
- 生命周期和输入有一个调用方所有者；快照读者不得与对象销毁并发。这仍需由
  后续服务层锁定生命周期，不把本轮 C ABI 直接当成多客户端 HTTP 服务。

容量只限制在途输入数量，不是整个进程或长期地图内存的上限。大点云单帧、
地图增长、额外快照几何副本仍需 ARM64 内存测量；本轮不能作为长时间建图批准。

## 修正点云

每次上游全局位姿更新后发布不可变快照：子图几何复制一次，各次快照持有该
几何和对应优化位姿的值副本。快照读者取得共享所有权后在锁外转换世界坐标，
不访问优化器正在修改的子图，也不继续累积旧里程计世界坐标。
缓冲区不足时返回当前规模和明确重试状态，不截断点云。

回放期间记录实际观察到的快照版本；停止后导出完整修正快照，与官方
`GlobalMapping::export_points()` 的保存点云按原顺序逐点比较，四组差异均为零。
这证明本轮最终导出的修正快照一致，不等于已经验收网页传输、并发读取压力、
现场地图精度或真实回环。

上游按关键帧生成子图，并非每个雷达扫描都生成完整修正地图。静止样本在
停止前没有完整子图快照，移动样本只观察到 1/3 次中间版本。产品接入必须
保留快速实时扫描预览，并区分尚未全局修正的数据，不能让用户等待子图完成
才看到雷达，也不能把旧预览累计结果冒充全局修正地图。

## 四组真实录制验证

使用 `tools/run_glim_async_mapping.py` 按原始 IMU 时间节奏输入，`--input-rate 1`。
静止与移动各保留两种尚未校准的扫描时间假设，没有按约束数量选择假设。

| 项目 | 移动/start | 移动/end | 静止/start | 静止/end |
| --- | --- | --- | --- | --- |
| 完整保存帧 | 1,190 | 1,189 | 313 | 311 |
| 子图 / 点 | 2 / 19,938 | 4 / 45,235 | 1 / 1,904 | 1 / 1,894 |
| 真实 IMU | 24,434 | 24,415 | 6,864 | 6,845 |
| 在途帧峰值 / 128 | 51 | 60 | 50 | 50 |
| 在途 IMU 峰值 / 8,192 | 494 | 1,199 | 10 | 12 |
| 拒绝 / 丢弃输入 | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| 输入侧最坏单帧，ms | 38.06 | 33.33 | 32.63 | 29.79 |
| 里程计和回调 P95，ms | 15.20 | 18.09 | 15.00 | 14.52 |
| 最大后台队列等待，ms | 2,443.46 | 5,975.05 | 31.72 | 36.94 |
| 最大后台任务，ms | 2,445.52 | 5,977.10 | 61.32 | 63.12 |

| IMU 扫描覆盖告警 | 1 | 1 | 0 | 0 |

四组均满足：原始扫描 = 未完整包围的扫描 + 初始化扫描 + 完整估计保存帧；
全部已接受完成帧和真实 IMU 被处理一次；保存图约束与增量记录一致；
独立新进程只读重载的完整地图清单、点数和点顺序一致；源码、录制、配置、
实际加载库和报告引用文件的摘要保持一致。重载最大差异约 `1.24e-6 raw`，
沿用 `1e-4 raw` 序列化容差，没有改尺度或误差门槛来通过。

源同步回放曾出现 2.40/5.53 秒的输入侧单帧阻塞。本轮观察到重计算不再阻塞
该调用链，但后台仍会延后约 2.4/6 秒，必须展示积压和最后更新时间。
不能用输入侧几十毫秒或快速入队宣称整张地图都在几十毫秒内完成优化。
有些回放在同一台电脑并行运行，这不是受控性能对比，更不是机器人性能保证。

本轮地图点数与同步回放并不完全相同，未以稀疏程度或外观判断精度。
两组移动样本各有一次真实 IMU-rate 扫描时长覆盖告警，未隐藏、抑制或当成
唯一误差来源；物理尺度、传感器时间、外参、几何和真实回环仍需独立测量。

## 验证与下一步

相关自动测试 108 项通过，无跳过。其中原生 C++ 测试真实启动工作线程，
每轮验证 FIFO、非计算线程执行、在途容量、满载锁存、异常传回、排空及
一次终结，重复 10 轮。合成测试没有被当成真实雷达、地图精度或运动验收。
匿名统计与源文件摘要见 `slam-async-mapping-evidence.json`；其导出工具重新
验证四份原生报告、每个引用文件和完整地图清单，不包含现场点云或坐标。

另将同一真实移动录制以 `--input-rate 0` 超速输入，不改变队列容量。
进程明确返回 `mapping_backlog_capacity_exceeded` 和非零退出码，留下失败报告，
没有生成 `map/`、保存点云或重载结果。该次是预期失败的过载检查，不计入
四组成功回放，也不以停止时再次收到同一锁存错误冒充正常停止成功。

下一步是把该链路接入 ARM64 实时采集和现有 Web 服务，在页面同时验证
快速扫描预览、修正子图更新、积压显示、停止排空与保存重载。完成静止检查、
给用户可打开的地图页面后，再协调测距路线的遥控复扫。本轮不部署机器人，
不覆盖厂商 AIMDK，不更改其导航或运动安全链路。
