# 连续导航卡住修复包部署说明

版本：`sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022`

`1.0.1` 额外修复 `1.0.0` 可能将共享日志目录从 `agi:sparkrobot-nav`
改成旧 bridge 进程主组的问题。该问题会让网页一键启动在执行
`mkdir /var/log/sparkrobot/lingxi-nav` 时报 `Permission denied`，并连锁导致灵心认证等待超时。

`1.0.2` 在保留连续导航修复的基础上增加语音预置动作接口。完整语音动作需要同时安装知识库包中的 Java Agent `1.0.4-20261022`；单独安装本包只更新导航 bridge，不会替换 Java Agent。

## 1. 适用故障

机器人能够完成第一个点位导航，也能播报并执行到点动作；程序随后显示第二个导航任务已开始，但机器人不走，目标距离长期保持不变，最后超时。

现场日志中的完整顺序是：

```text
第一个点完成，最终距离约 0.075m
SDK motion accepted: motion=1002, area=1, state=400, code=0
Stopping arrival motion with empty action
SDK motion accepted: motion=0, area=0, state=400, code=0
第二个 Navigation task started
目标距离长期保持约 7.03m
```

`state=400` 在 AIMDK 的 `CommonState.msg` 中表示 `RUNNING`，只代表请求正在运行，不是“动作已经完成”。旧程序在普通挥手等有限动作结束后仍发送 `0/0` 空动作，可能让 `interaction` 控制源继续占用运动控制，导致优先级较低的 PNC 已收到任务但无法驱动底盘。

诊断包同时证明 `/slam/lidar_odom` 有 1 个发布者、bridge 正在订阅，PNC 请求话题有订阅者；因此不是网页没有提交第二个任务，也不是 bridge 主线程卡死。诊断包当时没有采集 MC 当前输入源，所以“`0/0` 导致控制权滞留”属于由重复时序高度支持的根因判断，最终仍需安装后的双点现场验收闭环。

## 2. 修复内容

- 普通有限动作，例如 `1002` 挥手，等待配置时长后自然结束，不再发送 `0/0`。
- 持续动作 `6001` 仍按原需求发送一次 `0/0` 中断，并在下一点前等待 1.5 秒释放控制权。
- 手动暂停、停止、任务抢占和明确的灵创中断仍允许发送 `0/0`。
- 地图如果误把 `empty_motion` 配成普通到点动作，bridge 会拒绝执行。
- 动作响应优先检查官方 `header.code`；非零错误码不会再被 `RUNNING` 状态误判为成功。
- `/aima/pnc/pnc_task_response` 没有发布者时不加载缺失的消息类型，继续使用里程计判定。
- PNC 回验最多探测 15 次；当前 AIMDK 缺少 Python 消息类型时永久停用，不再每 2 秒无限刷错误日志。
- 保留 PNC 失败终态的异步清理方法，避免未来恢复响应发布者后在失败分支抛出属性错误。
- 重启前校验旧 PID 对应的确是导航 bridge；陈旧 PID 绝不会导致其他进程被误停。
- 正式产品固定使用 `agi` 运行导航 bridge，禁止继承旧热修复留下的 root 运行身份。
- 安装和每次重启前自动恢复 `/var/log/sparkrobot/lingxi-nav` 和 PID 目录的 `sparkrobot-nav` 共享组权限，保证 `agi` 与 `run` 都能从网页启动服务。
- 重启前先导入 ROS、AIMDK 和修复后的导航模块；导入失败时不停止正在运行的旧 bridge。
- 新增 `/motion/play` 白名单接口：只接受已核验的原始语音祈使口令，导航中或讲解任务进行/暂停时拒绝提交；不接受直播弹幕触发。

本包只更新：

```text
lingxi_nav_bridge.py
motion_option_policy.py
sdk_motion_controller.py
navigation_client.py
pnc_response.py
voice_preset_motion.py
```

不会修改 AIMDK、语音配置、灵心参数、Java Agent、知识库、地图数据或灵创资源。

语音动作白名单包含：挥手、握手、举手、飞吻、比心、击掌、敬礼、平举、拥抱、加油、鼓掌、双手打叉、胸前挥手、鞠躬、拜拜、动感光波、挠头、抓屁股。此 bridge 包负责最后一道原文与运行状态校验；Java Agent 负责只从明确祈使口令提出动作请求。问句、否定、引用/转述、条件表达和直播弹幕不触发动作。播报只确认请求已受理，不代表机器人已完成动作。

## 3. 旧完整包中确认的问题

`lingxi-v1.3.1-complete-20260906-r6` 的附加能力安装顺序是：

1. 灵创附加包 `1.0.3` 覆盖 `lingxi_nav_bridge.py`，其中正常换点仍发送 `0/0`。
2. PNC 修复包 `1.0.1` 只覆盖 `navigation_client.py` 和 `pnc_response.py`，没有修复动作收尾。
3. 该 PNC 版本还会对没有发布者或缺失 Python 类型的回验话题持续重试并刷日志。
4. 旧 PNC 运维脚本在 `set -u` 状态直接加载 ROS 环境，部分机器会报 `AMENT_TRACE_SETUP_FILES: unbound variable`；新运维脚本只在加载厂商环境时临时关闭 nounset。

因此，旧完整包即使安装和 `doctor` 通过，也仍可能出现本次连续导航卡住问题。

## 4. 从 Windows 上传

在存放安装包的 Windows PowerShell 目录执行，把 `机器人IP` 替换为实际地址：

```powershell
scp .\sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022.tar.gz run@机器人IP:/home/run/
scp .\sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022.tar.gz.sha256 run@机器人IP:/home/run/
```

登录机器人：

```powershell
ssh run@机器人IP
```

## 5. 安装

在机器人 `run` 账号中执行：

```bash
cd /home/run
sha256sum -c sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022.tar.gz.sha256
tar -xzf sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022.tar.gz
cd sparkrobot-lingxi-consecutive-nav-fix-1.0.2-20261022
sudo bash ./install.sh
```

安装器会依次执行：包内 SHA-256 校验、目标版本兼容性检查、Python 语法检查、原文件备份、原子替换和导航 bridge 重启。新 bridge 启动失败时会自动恢复原文件并尝试拉起旧 bridge。

如果已安装 `1.0.0` 且网页正显示日志目录权限错误，也可先执行以下现场恢复命令，无需等待新包：

```bash
sudo install -d -o agi -g sparkrobot-nav -m 0770 /var/log/sparkrobot/lingxi-nav /var/log/sparkrobot/lingxi-nav/ros /var/lib/sparkrobot/lingxi-nav/pids
sudo find /var/log/sparkrobot/lingxi-nav -type d -exec chgrp sparkrobot-nav {} + -exec chmod 0770 {} +
sudo find /var/log/sparkrobot/lingxi-nav -type f -exec chgrp sparkrobot-nav {} + -exec chmod 0660 {} +
```

然后回到网页再点一次“一键启动全部服务”。

不要使用无 sudo 权限的 `agi` 账号安装。如果机器人没有 `run` 账号的 sudo 权限，需要由设备管理员执行同一条 `sudo bash ./install.sh` 命令。

如果必须先复制文件、稍后维护窗口再重启：

```bash
sudo bash ./install.sh --no-restart
sudo sparkrobot-lingxi-consecutive-nav-fix restart
```

如果 `current` 软链接确实缺失，先修复正式部署的软链接。只有在明确知道实际目录时才可指定：

```bash
NAV_DIR=/opt/sparkrobot/lingxi-nav/releases/实际版本/navigation/robot_local_navigation_v3 \
sudo -E bash ./install.sh --no-restart
```

## 6. 不移动机器人的验收

```bash
sudo sparkrobot-lingxi-consecutive-nav-fix status
sudo sparkrobot-lingxi-consecutive-nav-fix doctor
```

`doctor` 检查：

- 6 个运行文件的 SHA-256；
- Python/ROS/AIMDK 模块导入；
- PNC 请求和响应话题的发布者、订阅者数量；
- MC 当前输入源和当前运动状态（接口存在时）；
- 最近的连续导航关键日志。

该命令不会发送导航、动作、重定位或语音指令。

如果 PNC 回验显示 `Publisher count: 0`，表示该机器人底层没有发布这个可选回验话题。修复后的 bridge 会停止有限探测并继续使用里程计到达判定，这不是连续导航再次卡住。

## 7. 现场双点验收

这一步会让机器人真实移动，必须由现场人员确认地图、定位和通道安全，并能够随时急停后再执行。

1. 在网页选择正确地图，确认 `/slam/lidar_odom` 有实时数据。
2. 新建只包含两个安全点位的讲解任务。
3. 第一个点先选普通挥手 `1002`，不要选灵创舞蹈。
4. 启动讲解，确认第一个点完成后第二个点的距离持续下降。
5. 日志应出现 `Arrival motion wait completed naturally`，且其后不应出现 `motion=0, area=0`。
6. 再单独验证 `6001` 时，日志应只出现一次空动作，并出现 `Tour task motion release wait started`。

实时观察日志：

```bash
sudo sparkrobot-lingxi-consecutive-nav-fix logs 500
```

## 8. 回滚

查看备份：

```bash
sudo sparkrobot-lingxi-consecutive-nav-fix backups
```

回滚最近一次安装并只重启导航 bridge：

```bash
sudo sparkrobot-lingxi-consecutive-nav-fix rollback latest
```

备份默认位于：

```text
/var/lib/sparkrobot/lingxi-consecutive-nav-fix/backups/时间戳/
```

## 9. 仍不走时需要收集的信息

若修复后第二点仍不走，不要连续重复下发任务。执行：

```bash
sudo sparkrobot-lingxi-consecutive-nav-fix doctor | tee /home/run/consecutive-nav-doctor.txt
sudo tail -n 1500 /var/log/sparkrobot/lingxi-nav/lingxi_nav_bridge.log > /home/run/lingxi-nav-last-1500.log
```

把这两个文件发回分析。重点核对 MC 输入源是否仍为 `interaction`、第二个 PNC 任务发布后里程计是否变化，以及是否还有其他程序持续下发运动控制。

## 10. 验收边界

本包已完成源码断言、语法、归档路径、权限、清单和 SHA-256 离线验证。离线验证不能等同于机器人真实运动验收；本次构建不会自动连接机器人，也不会自动执行导航。

构建审计还会在临时目录完成一次完整安装与恢复：模拟旧版 4 个既有文件和 2 个新增文件，核对备份、6 文件替换、安装清单、回滚内容及新增文件删除。该测试不连接 ROS，也不会控制机器人。
